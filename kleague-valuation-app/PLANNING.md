# K리그 선수 몸값 측정 앱 — 기획서 (v0.1)

> 별도 프로젝트. 이 레포의 기존 WorldDesk(인스타 릴스 파이프라인)와는 무관하며,
> `kleague-valuation-app/` 하위에 독립적으로 개발한다.

## 1. 개요

- **한 줄 정의**: K리그 선수들의 "현재 몸값"과 "예상 몸값"을 비교해 보여주고,
  사용자들이 그 평가에 대해 토론할 수 있는 모바일 앱.
- **타겟**: K리그 팬, 축구 커뮤니티/이적 루머 관심층, 판타지 축구 유저.
- **핵심 가치**: 해외 이적시장 데이터 + K리그 특화 변수를 결합한 몸값 추정치를
  "현재가 vs 예상가" 형태로 제시해, 저평가/고평가 선수를 한눈에 파악하게 함.
- **플랫폼**: 모바일 앱 (React Native + Expo, iOS/Android 동시 대응).

## 2. 핵심 기능

### 2.1 몸값 표시 — 현재 몸값 / 예상 몸값

- 선수 카드/상세 화면에 두 값을 나란히 표시:
  - **현재 몸값**: 참조 데이터(Transfermarkt 등) 기준값
  - **예상 몸값**: 자체 보정 알고리즘 산출값
- 표시 형식: `현재 15억 3,000만원 → 예상 22억원` (저장 단위는 "만원", 화면에는
  억 단위로 변환해 가독성 확보. 원 단위 raw 값도 API에서는 만원 정수로 유지)
- 예상가 - 현재가 차액을 %와 색상(상승=빨강/하락=파랑 — 국내 증권 관례)으로 강조
- 최근 변동 이력(스파크라인)은 Phase 2 이후

### 2.2 몸값 산정 로직

**현재 몸값**
- Transfermarkt 등 해외 이적시장 사이트의 공개 몸값을 1차 기준값으로 참조
- 크롤링은 이용약관/robots.txt 준수 범위 내에서만 수행하고, 화면에 출처·수집일
  명시. 약관상 어려우면 수작업 정기 업데이트로 전환할 수 있도록 파이프라인을
  소스 추상화해둔다 (Phase 1 오픈 이슈 참고)

**예상 몸값 (자체 알고리즘)**
- 기준값(현재 몸값)에 K리그 특화 보정 계수를 곱하는 구조:

  ```
  예상몸값 = 참조몸값 × f(최근폼) × f(나이) × f(출전시간·포지션기여도)
                     × f(계약잔여기간) × f(대표팀·이벤트) × f(에이전트보정)
  ```

- 보정 계수 상세:
  | 계수 | 반영 요소 |
  |---|---|
  | `f(최근폼)` | 최근 5~10경기 평점, 득점/도움, (가능하면) xG/xA |
  | `f(나이)` | 포지션별 전성기 곡선 (예: 공격수 24~28세 피크) |
  | `f(출전시간·기여도)` | 출전시간 대비 팀 기여 지표 |
  | `f(계약잔여기간)` | 잔여계약 짧을수록 할인, FA 임박 시 큰 폭 할인 |
  | `f(대표팀·이벤트)` | 국가대표 발탁, 해외 이적설 등 이벤트성 가점 |
  | `f(에이전트보정)` | 아래 3항 참고 |

- **에이전트 자문 반영 (사용자 요구사항 2번)**: 순수 통계 모델만으로는 "실제
  이적시장에서 통하는 가격"과 괴리가 생길 수 있음. 이를 보완하기 위해:
  1. 축구 에이전트/스카우트 자문단(비공식 인터뷰 또는 설문)에게 분기별로
     주요 선수 표본에 대한 "체감 몸값 레인지"를 수집
  2. 수집된 값과 알고리즘 산출값의 오차를 분석해 보정 계수 `f(에이전트보정)`를
     주기적으로 재조정 (사람이 수동으로 계수 업데이트하는 방식으로 시작,
     추후 회귀모델로 자동화 검토)
  3. 각 선수 상세 화면에 "알고리즘 추정" vs "에이전트 자문 반영" 두 수치를
     구분 표시해 신뢰도를 투명하게 공개

### 2.3 댓글/커뮤니티

- 선수별 댓글 스레드 (몸값에 대한 의견, 대댓글 지원)
- 좋아요, 신고 기능 (신고 누적 시 자동 숨김 → 운영자 검토)
- (옵션) "내가 생각하는 몸값" 사용자 투표 — 크라우드 위즈덤을 알고리즘과
  나란히 비교 표시하면 재미 요소 + 향후 보정 데이터로도 활용 가능
- 욕설/도배 필터링 기본 적용, 계정당 일일 댓글 한도 설정

## 3. 데이터 모델 (개략)

```
Player        (id, name, team_id, position, birth_date, contract_until, nationality, photo_url)
Team          (id, name, league_id)
League        (id, name)  # K리그1/K리그2 구분
ValuationSnapshot
              (id, player_id, snapshot_date,
               current_value_10k_won,      # 만원 단위
               predicted_value_10k_won,
               formula_version, source, agent_adjusted BOOLEAN)
AgentReview   (id, player_id, agent_alias, review_date, suggested_range_low, suggested_range_high, note)
User          (id, nickname, auth_provider, created_at)
Comment       (id, player_id, user_id, parent_comment_id, body, like_count, report_count, created_at)
ValuationVote (id, player_id, user_id, guessed_value_10k_won, created_at)   # 옵션 기능
```

## 4. 아키텍처 제안

- **모바일**: React Native + Expo (iOS/Android 동시 개발, 빠른 배포·업데이트)
- **백엔드**: Node.js (NestJS) + PostgreSQL, REST API
- **데이터 수집 파이프라인**: 별도 Python 배치 잡 (정기 스케줄) — 참조 사이트
  약관 검토 후 수집 방식(크롤링/수동/제휴 API) 확정
- **인증**: 소셜 로그인 (Google/Apple) + 이메일
- **푸시 알림**: 관심 선수 몸값 변동 시 알림 (Phase 3)

---

## 5. 법적·윤리 리스크

- Transfermarkt 등 사이트 데이터는 이용약관상 자동 수집이 제한될 수 있음 →
  참고 지표로만 활용 + 출처/수집일 명시, 필요 시 제휴 문의 또는 수작업 전환
- 선수 사진/통계 사용 시 초상권·저작권 확인 필요
- 댓글의 명예훼손·저작권 침해 리스크 → 신고 체계, 운영 정책(약관) 필수
- "몸값"이라는 표현이 실제 이적료를 보장하지 않는다는 면책 문구 명시 필요

---

## 6. MVP 로드맵

1. **Phase 1**: 선수 20~30명 수동 큐레이션 데이터 + 현재/예상 몸값 표시 화면
2. **Phase 2**: 자동 보정 알고리즘 v1 적용 + 댓글 기능
3. **Phase 3**: 에이전트 자문 반영 프로세스 정식 도입, 투표 기능, 변동 알림

---

## 7. 열린 이슈 (의사결정 필요)

- 참조 데이터 소스 확정 방식: 크롤링 vs 수작업 vs 공식 제휴
- 몸값 화면 표기 단위 최종안: "만원" 그대로 vs "억 단위" 변환 표시
- 수익 모델: 광고 / 구독 / 무료 여부
- 에이전트 자문단 실제 섭외 방법 (지인 네트워크, 커뮤니티 공모 등)
